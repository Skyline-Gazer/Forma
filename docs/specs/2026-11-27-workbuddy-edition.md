## 1. Product outcome

Forma becomes a WorkBuddy-native document organization Expert, not a standalone application. A user summons Forma in the existing client, selects a source and destination folder, asks to organize business documents, reviews a concise proposed plan, approves it, and receives an applied archive with reasons, exceptions, and a verification report. If DEVONthink is selected, indexed records and business metadata are written and read back; ordinary folder organization remains usable without DEVONthink or OneDrive. OneDrive stores original files, DEVONthink manages its own database and references. Project is optional shared context; Buddy App is a future packaging option, not a dependency. Do not implement a custom runtime, UI, model router, database, search engine, OCR engine, storage provider, or general workflow framework.

Alpha scope: Organize (inspect, plan, approve, apply, verify, recover) only. Incremental update is a subsequent acceptance slice after Alpha owner experience approval; historical audit and knowledge retrieval are backlog, not new implementation mandates. No autonomous scheduled production writes. No market submission, migration or public release without approval.

## 5. Functional requirements

FR1 Input: explicitly selected source root and authorized destination; dry-run by default; enumerate file identity, size/type, hash where justified, and unreadable/offline/unsupported state. Avoid following symlinks or fetching unrelated cloud files. Existing files outside selected scope not scanned or moved. Detect conflicts, extension and content mismatch. Do not use production corpus.
FR2 Perception: PDF, DOCX, XLSX, PPTX, TXT; DocVortex/available native parsers, Vision fallback for scans on macOS; preserve page/sheet/section evidence, table relationships and extraction failure reasons. Long docs use bounded chunks and retrieve relevant evidence; no filename-only classification or silent truncation. Cloud OCR/Jev optional only when justified and explicitly approved; no assumption of free API or accuracy from confidence.
FR3 Reasoning: LLM infers business identity, role, intent, project boundaries, buyer, bidder, vendor, document status/version and cross-document relationships from content and corpus context. Do not hard-code a universal taxonomy or enumerate regex classification rules. User can specify naming policy; preserve meaningful names, separate shared reference and ambiguous files, avoid invented fields, allow reasonable alternate shallow structures. Detect duplicates by content but do not delete or overwrite. Preserve original bytes/extensions. Document instructions are untrusted data, not commands.
FR4 Plan: machine-readable immutable plan plus readable preview. Include stable source identity, source/destination, disposition (move/rename/keep/review), evidence, metadata changes, conflict and uncertainty, input snapshot, schema version and plan ID/hash. Summary shows counts, proposed structure, exceptions, and original→new paths. User can correct plan and regenerate; no mutation until explicitly approving exact plan and scope. Changed files or changed plan invalidate approval. A safe refusal is not successful execution.
FR5 Execution: reuse deterministic validation and execution tooling. Check containment, symlink escapes, source hashes, stale plans, collision including case/Unicode, duplicate destinations, permissions, available space and single-writer boundary. No shell interpolation of untrusted paths. No silent overwrite/delete or external writes. Journal before/after, idempotency, explicit error/partial states, resume or rollback with conflict checks; do not undo independent user edits. Empty legacy directory cleanup only as separately previewed/approved operation, no recursive deletion. Prefer same-volume atomic move where possible; cross-volume/provider operations require explicit supported handling and verification or refusal. Verify original inventory and actual output mapping; preserve audit evidence locally.
FR6 DEVONthink optional: choose explicitly isolated/test database, index originals (do not import duplicate bytes), write approved tags/custom fields using existing supported APIs/AppleScript, read back actual values and record UUID/link/path. Reuse #10 existing field contract after audit; avoid inventing mandatory 12-field schema if not needed, do not fabricate metadata. Separate original file state from DEVONthink record state; on partial metadata failure report exactly what succeeded and allow safe retry/compensation. No promise of cross-system atomic transaction. Smart Groups use supported native UI or API, no external SQLite merely because a specific query syntax failed. No write to production DB or global preferences.
FR7 OneDrive optional: use selected File Provider folder as original storage, never active DEVONthink DB on OneDrive. Avoid bulk hydration outside requested scope. No independent storage/eviction implementation. Verify actual Finder native release and provider state after syncing, browse/search/restart/open selective file, quantify actual allocated bytes and unintended downloads; use meaningful larger synthetic files rather than only tiny fixtures. Separate local metadata retention from fresh-device sync/restoration; missing environment = BLOCKED/NOT_VERIFIED. No forced NSFileProviderManager probe or network configuration changes to bypass blocker.
FR8 Privacy: actual model/API route, content egress, extraction/log retention documented; synthetic data only unless owner separately authorizes exact destination and dataset. Never log credentials or publish gold, real paths/content, tokens, or private metadata. Local processing does not imply local model inference. No unapproved downloads/installations, privilege escalation, global appearance/TCC changes or unrelated host modifications.

Freeze rubric and independently sourced gold before outputs. Mean >=90/100, each run >=85, 3/3 flows. Project and version accuracy 100% for determinable items, role accuracy >=95%, zero cross-project errors, shared-to-exclusive misfiles, forced ambiguous attribution, data loss/overwrite/escape; correction rate <=5%. Report counts/denominators, reasonable confirmation separately from erroneous output, unnecessary abstention and straight-through coverage; no empty-denominator PASS or withholding difficult determinate items to inflate accuracy. Record actual time/tokens/cost or NOT_VERIFIED. Final human-time saving >=80% vs measured matched manual workflow, including review/confirmation. Storage/recovery gates separate; no substitution with semantic score. Any required gate unknown => conditional/no production GO. A failed gate gets one targeted low-cost remediation proposal with evidence; stop if no credible path. No endless benchmark tuning.
Final decision #216: adopt as-is, minimal adaptation, alternative storage/host, or stop; cost/maintenance and owner approval required. No automatic resumption of full Forma.

## 10. Consolidated product-contract amendments — adjudicated 2026-11-28 (Owner decision gate)

Single canonical amendment record consolidating the joint A/B/C reports, the #223 review and the DEVONthink 4.4.2 MCP verification. The Implementation Plan derives only after Owner approval of this section; nothing here re-authorizes production writes, migration or release.

- **10.1 Business metadata (D1, option A with required coverage).** The field set must cover project identity, document version, document status, document business date, vendor relationship and version linkage. Prefer reusing the legacy identifiers (`projectname, completionyear, bidderentity, department, salesowner, endcustomer, biddeadline, tenderreference, bsdcode, documentcategory, documenttype, issuer`) where semantics match. Business year is distinct from completion year; unknown values are never fabricated. The DEVONthink default six-field mapping alone is insufficient for long-term management and is superseded by the Profile field contract.
- **10.2 Naming (D2, template-default).** Names are generated deterministically from the Approved Organization Profile template; the LLM never assigns free-form names; files already conforming to the template keep their existing names.
- **10.3 Structure policy (D3, profile-only).** Directory partitions, hierarchy, naming templates, tags and metadata mapping live in the versioned Profile and are enforced by deterministic kernel validation; the LLM performs semantic field extraction and business judgement only. The Roadmap six-partition proposal is default template material for Profile 1.0, not an additional rule set.
- **10.4 Tags (D4, derived now).** Decided immediately on verified DEVONthink 4.4.2 MCP tag evidence; custom metadata keys are restricted to the Approved Profile whitelist and unknown keys must never auto-create database fields.
- **10.5 Project & relation model (D5, minimal).** Project registry; document-to-project N:1 with evidence; roles mutually exclusive; shared reference files belong to no single project.
- **10.6 Profile lifecycle (D6, seed-legacy).** `profile-1.0` seeded from the legacy corpus taxonomy; `grants_execution=false` always; plan approval binds `profile_hash`; semver with explicit supersede chain; storage in `~/.forma-workbuddy/profiles/` plus repository templates.
- **10.7 Sorty reuse (D7, patterns-only).** Forma absorbs Sorty's mature design and legally reusable capability — notably the 26 platform-independent pytest kernel patterns — without introducing a second file-operation kernel, without GPL code or binary distribution, and without inheriting its permissive authorization strategy. See REUSE_MATRIX.
- **10.8 Deterministic safety clauses (P0 convergence; tracked separately, NOT closed by #224).** Plan must reject any operation whose source entry eligibility is not INCLUDE; `SKIP_VERIFIED` must re-verify the destination before skipping; null or missing source hashes fail closed in drift check, recheck and verify; journal recovery must run under the single-writer lock, honor the plan-hash gate and contain every rollback path; `source_id` must follow the frozen product contract `docs/SPEC.md` §4.1 (no `dev:inode` coupling). A signature-probe read failure is treated as unreadable (fixed at bf20192); a declared protection fact that was never probed cannot yield EXCLUDE. The fallback-INCLUDE default direction is a flagged design gap pending a separate Owner decision.
- **10.9 Metadata publication chain (ordered).** Approved Profile → Inventory snapshot → Content extraction → Structured business metadata → Pre-plan reconciliation → Deterministic organization plan → Validation → Owner approval (binding plan, profile and metadata hashes) → File apply → DEVONthink index & metadata publication → independent-validator readback → persistent state. DEVONthink MCP offers no cross-tool transaction; the publication contract is pre-read → write → readback → ledger, marking published only on full consistency.
- **10.10 DEVONthink 4.4.2 MCP capability matrix (verified).** 62 tools at localhost:8420, `auth.required=false`; `get/set_record_tags` round-trips reliably (only AppleScript tag enumeration is broken); `set_record_custom_metadata` supports replace/merge and auto-creates fields for unknown keys (whitelist defense point); twelve native custom-field types via `list_custom_metadata_fields`; `metadata:` prefix search is unreliable (zero results); Smart Group creation is UI-only; record UUIDs are stable across rename, same-volume moves, parent-directory changes and content updates; cross-device identity is NOT_VERIFIED.

It is regression evidence only; #220 end-to-end acceptance remains open and must run against a package built from merged `workbuddy/dev`.
