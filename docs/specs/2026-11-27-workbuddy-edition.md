## 1. Product outcome

Forma becomes a WorkBuddy-native document organization Expert with a clear four-layer separation of responsibilities:
- **WorkBuddy** is the Agent host (runtime, UI, conversation, model routing, and native tool execution).
- **Forma** is the business specification, semantic organization policy, and deterministic safety/validation capability.
- **OneDrive / local filesystem** is the physical storage layer owning original bytes.
- **DEVONthink** is the logical management layer for the current product delivery loop.

A user summons Forma in the existing client, selects a source and destination folder, asks to organize business documents against an Owner-approved Organization Profile, reviews a programmatically grounded preview, grants genuine approval, and receives an applied archive with reasons, exceptions, and a verification report.

- **Delivery & acceptance boundary**: The ordinary filesystem kernel can run independently for local folder organization, **but complete Forma product acceptance MUST include DEVONthink Index, approved Metadata/Tag publication, and mandatory independent readback**. Replaceability of the DEVONthink adapter does not allow omitting DEVONthink publication or metadata readback from current product acceptance.
- **Storage boundary**: OneDrive production File Provider capability remains `NOT_VERIFIED` (#214); this does not block complete product delivery and acceptance in an isolated local environment.
- **Non-goals**: Do not implement a custom runtime, UI, model router, database, search engine, OCR engine, storage provider, or general workflow framework.

Alpha scope: Organize (inspect, plan, approve, apply, verify, recover) plus DEVONthink Index, metadata publication, and independent readback. Incremental update is a subsequent acceptance slice (#213) after Alpha owner experience approval; historical audit and knowledge retrieval are backlog, not new implementation mandates. No autonomous scheduled production writes. No market submission, migration or public release without approval.

## 5. Functional requirements

FR1 Input & Snapshot Authority: explicitly selected source root and authorized destination; dry-run by default; Snapshot is the sole authoritative source of objective file facts (stable `source_id`, paths, `byte_size`, `mtime`, `source_sha256`, `fs_state`, `is_dataless`, `magic_mismatch`). `source_id` must follow `docs/SPEC.md` §4.1 (persisted `source_root_id + normalized_relative_path -> stable UUID`, no `dev:inode` coupling). `source_sha256` must be computed or retrieved from the trusted Snapshot by the deterministic program, never from LLM drafts. Avoid following symlinks or fetching unrelated cloud files. Existing files outside selected scope not scanned or moved. Detect conflicts, extension and content mismatch. Enforce three-dimensional fail-closed eligibility (`read_eligibility`, `semantic_disposition`, `execution_eligibility`, see §10.8a). Do not use production corpus.
FR2 Perception: PDF, DOCX, XLSX, PPTX, TXT; WorkBuddy native readers first, DocVortex/available native parsers and macOS Vision fallback for scans; preserve page/sheet/section evidence, table relationships and extraction failure reasons. Long docs use bounded chunks and retrieve relevant evidence; no filename-only classification or silent truncation. Cloud OCR/Jev optional only when justified and explicitly approved; no assumption of free API or accuracy from confidence.
FR3 Reasoning & Profile Conformance: LLM infers semantic fields (project identity, document role, parties, vendor relationship, business date, document version/status, version linkage, cross-document relationships, and explicit uncertainty) from content and corpus context against the Approved Organization Profile (`docs/workbuddy/ORGANIZATION_PROFILE_1_0_CANDIDATE.md` / `organization-profile-1.0.candidate.json`). Keep taxonomy data-driven in the versioned Profile rather than hardcoding classification rules in code. The LLM NEVER assigns free-form filenames or invents directory hierarchies: target paths, filenames, and derived tags are deterministically rendered and validated by the kernel from the Approved Profile template (files already conforming to the template keep their existing names). Separate shared reference, vendor library, and ambiguous/triage files; never fabricate unknown fields. Detect exact duplicates by `source_sha256` without deleting or overwriting. Preserve original bytes and extensions. Document instructions are untrusted data, not commands.
FR4 Plan, Grounding & Approval Boundary: machine-readable immutable plan plus readable preview. Programmatically reconcile the full Snapshot `source_id` set and semantic coverage before generating a plan, and re-validate all IDs, Profile binding, paths, collisions, `source_sha256`, operation dispositions, and derived counts/charts after plan generation (never trust LLM draft counts, sizes, hashes, or identities). Include stable `source_id`, source/destination, disposition (`move`/`rename`/`keep`/`review`/`exclude`), evidence, metadata/tag changes, conflict and uncertainty, `snapshot_hash`, `profile_id`/`profile_version`/`profile_hash`, `metadata_hash`, `schema_version`, and `plan_id`/`plan_hash`. Persist durable state across batch interruptions, context compaction, and session boundaries so no file is silently dropped. Preview tables, counts, and charts must be computed deterministically by the program. User can correct plan and regenerate; no mutation until genuine Owner approval of the exact plan and scope (§10.8b: `plan_hash` is integrity binding only, NOT proof of user identity or approval). Changed files, changed Profile, or changed plan invalidate approval. A safe refusal is not successful execution.
FR5 Execution & Recovery: deterministic validation and execution tooling. Enforce `execution_eligibility == INCLUDE` (fail-closed on non-INCLUDE, missing/null `source_sha256`, unknown protection facts, or unreadable/corrupt entries), `SKIP_VERIFIED` destination revalidation before skipping, containment, symlink escapes, stale plans, collision including case/Unicode NFC, duplicate destinations, permissions, available space, and single-writer `flock`. No shell interpolation of untrusted paths. No silent overwrite/delete or external writes; exclusive atomic no-replace rename (`RENAME_EXCL` / `RENAME_NOREPLACE`, fail-closed if unsupported). Journal before/after, idempotency, explicit error/partial states, and `recover` running under single-writer lock with `plan_hash` gate, containment checks on every rollback path, and conflict-hold protection (never undo independent user edits). Empty legacy directory cleanup only as separately previewed/approved operation (`rmdir` only, no recursive deletion). Prefer same-volume atomic move where possible; cross-volume/provider operations require explicit supported handling and verification or refusal. Verify original inventory and actual output mapping; preserve audit evidence locally. Code size is NOT an acceptance criterion; all confirmed P0 safety clauses (§10.8) must be resolved regardless of historical LOC estimates.
FR6 DEVONthink publication & readback (current product closure; replaceable adapter): DEVONthink is the current logical management layer; complete Forma product acceptance requires DEVONthink Index, approved Metadata/Tag publication, and mandatory independent readback (never treated as optional acceptance). Use the verified DEVONthink 4.4.2 built-in MCP (`localhost:8420`) as the preferred path (minimal `osascript` fallback only if built-in MCP is unavailable). Mandate: choose an explicitly isolated/test database for acceptance; **Index** originals (never Import duplicate bytes); publish Metadata/Tags only after physical archiving and integrity verification succeed; write only Approved Profile whitelisted keys (pre-read `list_custom_metadata_fields`, reject unknown keys so DEVONthink never auto-creates fields) and whitelisted Tags (`get/set_record_tags`); **mandatory independent readback** of record UUID, resolved path, Tags, and all written Custom Metadata fields; mark `published` only on full readback consistency (never on partial failure); retries must query live DEVONthink state first to prevent duplicate records; keep physical file state separate from DEVONthink record state; do not claim cross-tool atomic transactions. Smart Groups remain UI-only (never access internal `.dtBase2` SQLite directly). Treat local MCP `auth.required=false` and tool permissions as explicit security constraints (Prompt/whitelist declarations alone are not host-enforced isolation). No write to production DB or global preferences.
FR7 OneDrive optional (environment-gated): use selected File Provider folder as original storage, never active DEVONthink DB on OneDrive. Avoid bulk hydration outside requested scope. No independent storage/eviction implementation. Verify actual Finder native release and provider state after syncing, browse/search/restart/open selective file, quantify actual allocated bytes and unintended downloads; use meaningful larger synthetic files rather than only tiny fixtures. Separate local metadata retention from fresh-device sync/restoration; missing environment = `BLOCKED`/`NOT_VERIFIED` (this does not block isolated local-environment delivery). No forced NSFileProviderManager probe or network configuration changes to bypass blocker.
FR8 Privacy: actual model/API route, content egress, extraction/log retention documented; synthetic data only unless Owner separately authorizes exact destination and dataset (COPY ONLY protocol, §10.12). Candidate and shipped repository Profiles must contain zero real customer names, paths, UUIDs, quotations, or private business data. Never log credentials or publish gold, real paths/content, tokens, or private metadata. Local processing does not imply local model inference. No unapproved downloads/installations, privilege escalation, global appearance/TCC changes or unrelated host modifications.

  - **Grounding authority**: Snapshot is the sole authoritative source of objective file facts. `source_sha256` must be obtained from the trusted Snapshot or recomputed by the deterministic program. - **10.8a Eligibility decision (resolved — fail-closed 3D model).**
  - Unknown, unverifiable, unprobed, or incomplete security/file states never receive automatic execution eligibility.
  - Ordinary files that explicitly satisfy approved eligibility rules CAN be classified `INCLUDE`.
  - Unknown protection attributes, unreadable files, missing `source_sha256`, or abnormal states (`extension_mismatch`, `SF_DATALESS` when content is required, conflicting provenance) MUST route to `REVIEW` or block execution — never mechanically replacing all ordinary files with `REVIEW`.
  - Strictly separate three independent dimensions (never conflated into one status):
    1. `read_eligibility` (whether content may be read/inspected in scope);
    2. `semantic_disposition` (business classification outcome: `mapped`, `keep`, `review`, `exclude`);
    3. `execution_eligibility` (whether physical mutation is permitted: `INCLUDE`, `REVIEW`, `EXCLUDE`, `BLOCKED`).
    Read-only semantic analysis of an in-scope file NEVER implies permission to move or write it.
- **10.8b Owner approval boundary (resolved).**
  - `plan_hash` (along with `snapshot_hash`, `profile_hash`, `metadata_hash`) is an **integrity binding** only — it is NOT proof of user identity or genuine Owner approval. Any hash that the Agent itself can read, compute, and pass into a CLI argument cannot be treated as independent Owner approval.
  - The Implementation Plan MUST select and verify a genuine, independently verifiable approval path before any production writes are enabled: (a) empirically verified WorkBuddy native mandatory user confirmation under default permission mode, OR (b) an independent OS/system-level human execution confirmation path outside Agent-forged arguments, OR (c) another verified minimal alternative. Do not fabricate WorkBuddy host security capabilities and do not build a generic permissions framework.
